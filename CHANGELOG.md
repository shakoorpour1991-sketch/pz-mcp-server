## [Unreleased]

### Removed

- **Legacy Build 41 script data purged** (B41 data audit, verified against the parsed 42.20 vanilla DB — zero items carry `Type`, `MaxHitCount`, or a `Torso`-style `BodyLocation`):
  - `ScriptGenerator` item templates now emit `ItemType = base:*` (never `Type = ...`); a legacy `Type` spec in user input is mapped onto `ItemType` instead of leaking into output. B41-only defaults removed: `DamageCategory` → `SubCategory` (Swinging), `CanBeEquipped` + `MaxHitCount` dropped, clothing `BodyLocation = Torso` → registry `base:tshirt` with bare `ClothingItem = Tshirt_DefaultTEXTURE` and valid `BloodLocation`
  - `ValidationEngine`: `Type`, `CanBeEquipped` and `DamageCategory` removed from known properties; `ItemType` is the required item property (legacy `Type` no longer satisfies it) with `ItemType`/`SubCategory` recognized; weapon/food block checks keyed on `ItemType = base:weapon` / `base:food`
  - `ModAnalyzer` balance baselines now use real B42 item classes (`base:weapon`, `base:clothing` incl. armor defense stats, `base:food`, `base:container`); the B41-era `Armor`/`Ammo` categories (which never matched any `Type`) were dropped — balance analysis now actually finds a baseline against Build 42 data
  - `DatabaseManager.getItemsByPropertyType` defaults to `ItemType`; modgen templates' legacy `Type` fallback baselines removed
  - Fixtures, unit/integration tests, deck examples (`admin/data.mjs`) and `docs/USAGE_EXAMPLES.md` updated to the Build 42 spelling

### Added

- **ZedScripts validation extended to all 97 block types (deep scan + hierarchy)** — the knowledge layer now validates every block type the dataset describes, not just the six primary ones. The shared scanner (`src/utils/scriptScanner.ts`) gained an opt-in **deep mode** (`nested` + `keywords`) that recognizes every dataset keyword (multi-token `component *` variants included) at any brace depth, producing nested blocks with a `parent` field; the parser's flat path is byte-for-byte unchanged. The rule engine validates each block against its own parameter knowledge (unknown/typo'd parameters, wrong values/types, missing required parameters like `character_trait_definition`'s six, deprecations, commas) with **hierarchy checks** (`WRONG_PARENT`/`MISSING_PARENT` — e.g. a `clip` at module level, a `component` inside a `craftRecipe`) and **context-aware ID rules** (`parentsWithout` — unnamed `sound`/`model` inside vehicles; `optional`). Nested components no longer leak their lines into the enclosing item/entity (this also fixed a latent false-positive class on real B42 scripts with `component FluidContainer` etc.); component-variant typos (`component FluidConatiner`) report `INVALID_ID` with the valid variants and a did-you-mean suggestion; `needsChildren` is satisfied by scanned child blocks (`face`/`contextEntry`) as well as inline sections (`inputs`/`outputs` stay dedicated-section validated). New suite coverage in `tests/unit/zedScriptsValidation.unit.test.js` (10 tests: entity/components/face/layer, nested `component FluidContainer`, variant typo, WRONG_PARENT, unnamed clip/sound, trait required params, valid fluid/model/timedAction/mannequin).

- **ZedScripts validation layer (deterministic diagnostics for AI-generated scripts)** — the server now integrates the [ZedScripts](https://github.com/PZ-Wiki-Modding/ZedScripts) extension's machine-readable knowledge as a validation/diagnostic source rather than documentation. The `pz-scripts-data` dataset it bundles (block types, parameters, types, allowed/default values, required flags, deprecations, dependent parameters, ID rules) is vendored verbatim into `src/validation/zedData/` by a mechanical port script (`scripts/port_zed_scripts_data.mjs`, provenance + commit recorded in `SOURCE.json`) and consumed by a new rule engine (`src/validation/zedScriptsKnowledge.ts` + `zedScriptsRuleEngine.ts`) that extends the existing `ValidationEngine` — no parallel validator. Ported diagnostics: unknown parameters (with typo suggestions), missing required parameters (e.g. `craftRecipe` `tags`), wrong values (`ItemType = base:sword`), wrong types (`Weight = heavy`), deprecated parameters (`Type`/`DisplayName` since 42.13.0 with replacements), duplicate parameters, missing values/commas, block-ID rules, unknown block keywords, and `craftRecipe` input/output shape issues (fractional amounts, missing module, dots/space in item ids, `*` with others). Every diagnostic is structured: file (when `filePath` is used), line, column, code, severity, property/value/expected, and an actionable suggestion; results carry the upstream dataset source + commit (version-aware). `validate_script` gained a `filePath` param (validate a script on disk, file-scoped diagnostics); `analyze_mod` script analysis is file-scoped and column-aware. Conflict resolution: legacy B41 `recipe` blocks keep the existing lenient handling (the dataset is B42-focused), server-verified params the dataset omits (`evolvedrecipe` `Ingredients`/`Time`) are allowlisted, and the server's own verified checks (required `ItemType`) win. New suite `tests/unit/zedScriptsValidation.unit.test.js` (20 tests: valid Build 42 scripts + intentionally invalid ones mimicking AI mistakes, incl. malformed amounts, comma-vs-semicolon lists and integral floats) plus 2 validationEngine tests (B42 craftRecipe now includes the required `tags`; a missing-`tags` recipe errors) and an integration test for `validate_script` with `filePath`. ### Fixed

- **`node:sqlite` `exec()` parameter gotcha** — tests that delete rows through a raw connection now use prepared statements: `exec('DELETE … WHERE id = ?', id)` silently ignores bound parameters and deletes nothing

### Fixed

- **Search-as-you-type (autocomplete / `search_vanilla`)** — `prepareFTSQuery` built exact-token FTS5 matches (`"flou"`), so partial prefixes like `flo`/`flou` returned nothing while typing and autocomplete felt dead. Terms are now prefix-matched (`flou*` → Flour2/Cornflour2), quoted for safety when a term still carries FTS punctuation (e.g. `Base.Burger`), multi-term input becomes an AND of prefixes, and operator/empty input still yields the match-nothing query. Works for the Chain seed autocomplete, the DB tab search, and any `search_vanilla` caller.
- **Recipe Chain fullscreen graph: inspector no longer blocks the toolbar / panning, and panning works at every zoom** — the empty-state "click a node" panel was a 320px overlay at the top-right that covered the fit/zoom/export buttons and ate drags in that region; it is now a tiny non-interactive hint pill at the bottom-center (`pointer-events: none`), and the real inspector anchors below the toolbar. The pan clamp previously hard-locked `pan = 0` whenever the graph fit the viewport (i.e. at the default fit zoom nothing could be dragged); it now uses soft bounds — the graph can slide ~40% of a viewport past each edge and settles on release, and overflowed graphs keep the viewport covered with a little overscroll. A manual drag also opts the view out of auto-refit on resize.
- **Recipe Chain graph: consumers for every item** — the chain graph read only the `references` table, which B42 bracket (`item 1 [Base.Plank;...]`) and tag (`item 1 tags[base:plank]`) inputs never reach, so items showed producers but no offspring (e.g. Plank had 3 producers, 0 consumers). The walk now loads the `recipe_ingredients` mirror (authoritative) + references + item tags once per call into an in-memory index:
  - Recipe nodes' ingredients/results/tools come from the mirror first (bracket alternatives + `tags[...]` inputs); tag inputs resolve to the items that actually carry the tag (tagged `tag: true` in the payload — inspector/markdown show a `tag` badge)
  - Item nodes' `producedBy`/`consumedBy` union mirror rows, legacy references rows, and the tag bridge (recipes consuming any of the item's tags) — live DB: Plank 3→36 consumers, Flour2 now shows 14 dough/baking recipes via `base:flour`
  - The parser now also emits mirror rows as `references` rows during `parse_game_files`, so fresh parses carry the same edges in both stores
