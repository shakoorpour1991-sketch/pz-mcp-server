### Added

- **Phase 5: semantic KB search — local WASM embeddings, fully opt-in (`docs/kb-v2-embeddings.md` Option A)** — the locked Phase 5 design ships end-to-end with **zero behavior change and zero downloads unless the user asks**:
  - **`embed_knowledge` tool (explicit, incremental, scriptable)** — backfills semantic vectors for every chunk missing one (or whose model changed), chunk text = `title + content`, batched; `dryRun: true` previews pending work without downloading/embedding/writing, `limit` caps a run. The model downloads **once** into `<data>/models/` (`<cacheDir>/<org>/<repo>/`) and persists across restarts — a second run over the cached model is provably network-free (unit-tested with an injected fake downloader). No model download at install, boot, or `index_knowledge_base`/`index_javadocs` time; embedding happens ONLY via `embed_knowledge`
  - **Schema v5 (purely additive)** — `knowledge_chunk_vectors` table (`chunk_topic` PK FK, `doc_topic`, `model`, `dims`, `vector` = Float32Array BLOB, `updated_at`) + `idx_kcv_doc` index; v2/v3/v4 DBs migrate in place, vectors backfilled on demand; orphan vectors pruned per run
  - **`search_knowledge_base { semantic: true }`** — hybrid retrieval: embed the query → brute-force cosine scan with typed arrays → top-K (50), merged with the FTS bm25 top-K and re-ranked by **0.7·bm25 + 0.3·cosine** (tunable consts), capped at `limit`, decorated with the existing metadata + rendered with the existing formatter. No keyword hit → semantic hits still returned (conceptual recall booster). `semantic: false` (default) is byte-identical to the FTS path
  - **Friendly errors, never crashes** — `semantic: true` with no vectors → "No semantic vectors indexed yet. Run embed_knowledge first…"; a stored model that differs from the current `PZ_MCP_EMBEDDING_MODEL` → guides a re-embed
  - **Runtime: pure WASM, zero native deps** — `@huggingface/transformers` pinned to **v3.8.1** with an npm override mapping `onnxruntime-node` → `onnxruntime-web` (the native module is never installed; the WASM runtime ships in the package). `src/knowledge/EmbeddingManager.ts` (injectable encoder + `TransformersEmbeddingEncoder`): lazy import so boot/index never touch it, model kept resident for query-time, `wasmPaths` as a `file://` URL of onnxruntime-web's local dist, `allowRemoteModels` gates the one-time download
  - **New env vars** — `PZ_MCP_EMBEDDING_MODEL` (default `Xenova/all-MiniLM-L6-v2`, change forces clean re-embed) and `PZ_MCP_EMBEDDING_BATCH_SIZE`, validated by the startup Zod schema in `src/utils/config.ts`
  - **Tests + docs** — new `embeddingManager.unit.test.js` (cosine + blend math, one-time-download policy) and `knowledgeBase.embeddings.unit.test.js` (v5 migration, incremental backfill, model-change re-embed, dry-run, no-vectors error, hybrid search, topic filter on the semantic scan) with a tiny stub encoder (NO model in CI); server integration coverage (`embed_knowledge` dry-run, `semantic: true` friendly error); tool-registry snapshot to **30 tools**; `scripts/_verify_kb.mjs` extended with v5 schema + vector-table checks; a latent FTS5 bug fixed (parenthesized multi-term expansion fallback is joined with explicit `AND` — FTS5 rejects implicit AND between `(...)` groups). Suite now **598 tests / 118 suites**; `npm run verify:kb` green. Admin deck untouched; Option B (API providers) out of scope

### Added

- **ZedScripts validation extended to all 97 block types (deep scan + hierarchy)** — the knowledge layer now validates every block type the dataset describes, not just the six primary ones. The shared scanner (`src/utils/scriptScanner.ts`) gained an opt-in **deep mode** (`nested` + `keywords`) that recognizes every dataset keyword (multi-token `component *` variants included) at any brace depth, producing nested blocks with a `parent` field; the parser's flat path is byte-for-byte unchanged. The rule engine validates each block against its own parameter knowledge (unknown/typo'd parameters, wrong values/types, missing required parameters like `character_trait_definition`'s six, deprecations, commas) with **hierarchy checks** (`WRONG_PARENT`/`MISSING_PARENT` — e.g. a `clip` at module level, a `component` inside a `craftRecipe`) and **context-aware ID rules** (`parentsWithout` — unnamed `sound`/`model` inside vehicles; `optional`). Nested components no longer leak their lines into the enclosing item/entity (this also fixed a latent false-positive class on real B42 scripts with `component FluidContainer` etc.); component-variant typos (`component FluidConatiner`) report `INVALID_ID` with the valid variants and a did-you-mean suggestion; `needsChildren` is satisfied by scanned child blocks (`face`/`contextEntry`) as well as inline sections (`inputs`/`outputs` stay dedicated-section validated). New suite coverage in `tests/unit/zedScriptsValidation.unit.test.js` (10 tests: entity/components/face/layer, nested `component FluidContainer`, variant typo, WRONG_PARENT, unnamed clip/sound, trait required params, valid fluid/model/timedAction/mannequin).
- **Mod Generator now surfaces structured script diagnostics** — `modgen_generate`/`modgen_regenerate` validation output carries `scriptDiagnostics` (every ValidationEngine + ZedScripts finding with file/line/column/code/severity/message/suggestion), the generated script's path (`scriptFile`), and ZedScripts knowledge-layer provenance (`zedScripts` source/commit) alongside the existing `ready`/`scriptWarnings` summary, so generated mods report _why_ they are (not) ready — the deck and tool output render them with severity icons. - **ZedScripts validation layer (deterministic diagnostics for AI-generated scripts)** — the server now integrates the [ZedScripts](https://github.com/PZ-Wiki-Modding/ZedScripts) extension's machine-readable knowledge as a validation/diagnostic source rather than documentation. The `pz-scripts-data` dataset it bundles (block types, parameters, types, allowed/default values, required flags, deprecations, dependent parameters, ID rules) is vendored verbatim into `src/validation/zedData/` by a mechanical port script (`scripts/port_zed_scripts_data.mjs`, provenance + commit recorded in `SOURCE.json`) and consumed by a new rule engine (`src/validation/zedScriptsKnowledge.ts` + `zedScriptsRuleEngine.ts`) that extends the existing `ValidationEngine` — no parallel validator. Test suite is now **454 tests / 95 suites**.
- **JavaDocs ingestion into the knowledge base** — new `index_javadocs` tool + a generic, automated ingestion pipeline (`src/knowledge/javadocs/`): recursively scans a generated JavaDoc tree and keeps only real API type pages (identified mechanically by the `javadoc/ClassWriter` generator meta tag — no manual file lists), parses each page programmatically with a dependency-free HTML parser into structured API knowledge (package, kind, fully-qualified name, modifiers, type signature, inheritance chain, superclass, implemented interfaces, description, deprecated flags, and every field/constructor/method with signature, return type, parameters, and javadoc descriptions), renders one markdown doc per type in the KB's preferred representation (frontmatter `title`/`source`/`version`/`kind`/`package` + structured body), and indexes it through the existing `KnowledgeBaseManager` so `search_knowledge_base` returns Java API results alongside the markdown docs.
